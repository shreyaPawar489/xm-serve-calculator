What these numbers mean

System capacityHow much traffic one GPU can serve at once while meeting its latency target.Benchmark: +30% on the same GPU. This is the gain we model.
ThroughputTotal tokens per second one GPU produces across all users.We assume capacity gain becomes the same % more tokens served at the same utilization. A pilot checks this.
Concurrent usersHow many sessions one GPU holds at once. More fast memory keeps more sessions' context loaded.Not modeled separately; measured in the pilot.
LatencyTime to first token and tokens per second per user, which is what each end user feels.Benchmark: +33–50% tokens/sec per user; up to 6.7× faster first token vs DRAM offload. Shown as a benefit, not counted in the dollars.

What this is based on

When this estimate may not apply. The +30% was measured by Netpreme on one H100-class GPU running Qwen3-30B-A3B (FP8) on an agentic serving benchmark (AIPerf, SGLang HiCache) with a 64 GB X-Mem offload tier. Short-prompt traffic, models that already fit in HBM, strict latency targets and non-NVIDIA accelerators may see less. The gain is not scaled with tray size: a 16 TB tray gives far more memory per GPU than the 64 GB tested. A pilot on your own traffic replaces these assumptions with measurements.

Proposed XM-Serve pilot

A technical evaluation on Netpreme's early-access Memory-Augmented VM, where a customer picks a number of GPUs and an amount of X-Mem memory and requests pilot time. Your setup from step 1 is attached.

How the evaluation works

  1. Baseline run. Your traffic, or a replay of it, on the GPUs without X-Mem, on vLLM or SGLang.
  2. X-Mem run. The same traffic on the same GPUs with the X-Mem tier added.
  3. Measure at your latency target: tokens/sec per GPU, concurrent sessions, time to first token (p50 and p95) and cost per 1M tokens.
  4. Compare with this estimate. Measured gain vs the used here. Within ±20% means the calculator can be trusted for your next decision; outside it, we recalibrate the defaults.
